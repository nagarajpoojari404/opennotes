Inference mem cost

LLM inference memory and throughput fundamentally split across two operating regimes governed by the Roofline Model: the prefill phase (time-to-first-token, compute-bound) and the decode phase (token generation, memory-bandwidth-bound).

1. Total Inference Memory Breakdown

Total inference memory consists of static weights, the dynamic Key-Value (KV) cache, and transient runtime activation scratchpads:

Mtotal=Mweights+MKV+Mruntime_buffersM_{\text{total}} = M_{\text{weights}} + M_{\text{KV}} + M_{\text{runtime\_buffers}}Mtotal​=Mweights​+MKV​+Mruntime_buffers​

A. Model Weights (MweightsM_{\text{weights}}Mweights​)

Unlike training, inference requires no optimizer states and no gradients:

Mweights=N×PweightM_{\text{weights}} = N \times P_{\text{weight}}Mweights​=N×Pweight​

  • FP16 / BF16: 2 bytes / param2\text{ bytes / param}2 bytes / param →Mweights=2N\rightarrow M_{\text{weights}} = 2N→Mweights​=2N

  • FP8 / INT8: 1 byte / param1\text{ byte / param}1 byte / param →Mweights=1N\rightarrow M_{\text{weights}} = 1N→Mweights​=1N

  • INT4 (GPTQ / AWQ / GGUF Q4_K_M): ≈0.5 to 0.56 bytes / param\approx 0.5\text{ to } 0.56\text{ bytes / param}≈0.5 to 0.56 bytes / param →Mweights≈0.55N\rightarrow M_{\text{weights}} \approx 0.55N→Mweights​≈0.55N

B. KV Cache Memory (MKVM_{\text{KV}}MKV​)

For autoregressive generation, keys and values computed for previous tokens are stored in VRAM to avoid O(s2)O(s^2)O(s2) recomputation:

MKV=2⋅L⋅hKV⋅dhead⋅s⋅b⋅PKVM_{\text{KV}} = 2 \cdot L \cdot h_{\text{KV}} \cdot d_{\text{head}} \cdot s \cdot b \cdot P_{\text{KV}}MKV​=2⋅L⋅hKV​⋅dhead​⋅s⋅b⋅PKV​

  • 222: Stores both Key and Value tensors

  • LLL: Number of transformer layers

  • hKVh_{\text{KV}}hKV​: Number of KV heads (in Grouped-Query Attention / GQA, hKV≪hQh_{\text{KV}} \ll h_{\text{Q}}hKV​≪hQ​, typically 888 vs 323232)

  • dheadd_{\text{head}}dhead​: Head dimension (usually 128128128)

  • sss: Total sequence context length (prompt tokens + generated tokens)

  • bbb: Batch size (concurrent requests)

  • PKVP_{\text{KV}}PKV​: Bytes per element (222 for FP16, 111 for FP8, 0.50.50.5 for INT4)

Example (Llama 3.1 8B): L=32L=32L=32, hKV=8h_{\text{KV}}=8hKV​=8, dhead=128d_{\text{head}}=128dhead​=128, FP16 cache (2 bytes2\text{ bytes}2 bytes):

KV per token=2×32×8×128×2=131,072 bytes=128 KiB / token\text{KV per token} = 2 \times 32 \times 8 \times 128 \times 2 = 131,072\text{ bytes} = 128\text{ KiB / token}KV per token=2×32×8×128×2=131,072 bytes=128 KiB / token

For a batch of b=16b=16b=16 requests at context s=8,192s=8,192s=8,192:

MKV=128 KiB×8,192×16≈16.78 GBM_{\text{KV}} = 128\text{ KiB} \times 8,192 \times 16 \approx \mathbf{16.78\text{ GB}}MKV​=128 KiB×8,192×16≈16.78 GB

2. Autoregressive Decode Speed (Tokens / Sec)

In the token generation (decode) phase with batch size b=1b=1b=1, the GPU performs roughly 2N2N2N FLOPs per token. Because every model parameter must be fetched from HBM into SRAM once per token, the arithmetic intensity is:

Arithmetic Intensity=2N FLOPsMweights bytes≈2 FLOPs2 bytes=1.0 FLOP/byte\text{Arithmetic Intensity} = \frac{2N \text{ FLOPs}}{M_{\text{weights}} \text{ bytes}} \approx \frac{2 \text{ FLOPs}}{2 \text{ bytes}} = 1.0 \text{ FLOP/byte}Arithmetic Intensity=Mweights​ bytes2N FLOPs​≈2 bytes2 FLOPs​=1.0 FLOP/byte

Modern GPUs have an arithmetic intensity ceiling of 100–300 FLOP/byte100\text{–}300\text{ FLOP/byte}100–300 FLOP/byte, meaning compute units sit idle waiting for memory. Single-sequence generation speed is strictly memory-bandwidth bound.

Analytical Formula:

Throughput (Tokens/sec)=Memory Bandwidth (GB/s)×ηMBUBytes Read Per Token (GB)\text{Throughput (Tokens/sec)} = \frac{\text{Memory Bandwidth (GB/s)} \times \eta_{\text{MBU}}}{\text{Bytes Read Per Token (GB)}}Throughput (Tokens/sec)=Bytes Read Per Token (GB)Memory Bandwidth (GB/s)×ηMBU​​

  • ηMBU\eta_{\text{MBU}}ηMBU​ (Memory Bandwidth Utilization): Real-world kernel efficiency (typically 60% to 75%60\% \text{ to } 75\%60% to 75% in engines like vLLM, TensorRT-LLM, or llama.cpp).

  • Bytes read per token: Mweights+MKVbM_{\text{weights}} + \frac{M_{\text{KV}}}{b}Mweights​+bMKV​​ (at moderate contexts, MweightsM_{\text{weights}}Mweights​ dominates).

When concurrent batch size bbb increases (continuous batching), the static weights are read once and reused across all bbb sequences. Generation transitions from memory-bound to compute-bound when:

b∗≈Peak Tensor TFLOPsMemory Bandwidth (TB/s)×Weight Precision Bytesb^* \approx \frac{\text{Peak Tensor TFLOPs}}{\text{Memory Bandwidth (TB/s)} \times \text{Weight Precision Bytes}}b∗≈Memory Bandwidth (TB/s)×Weight Precision BytesPeak Tensor TFLOPs​

4. Batched Serving Throughput (Compute-Bound Scaling)

For cloud inference serving (e.g., serving 64 concurrent users simultaneously on an H100):

  • Single-user generation is latency-optimized (∼146 tok/s\sim 146\text{ tok/s}∼146 tok/s, GPU compute is mostly idle).

  • Batched generation (b=64b=64b=64) is throughput-optimized:

    Aggregate Tokens/Sec≈Active FP16 Tensor TFLOPS×MFU2⋅N⋅1012\text{Aggregate Tokens/Sec} \approx \frac{\text{Active FP16 Tensor TFLOPS} \times \text{MFU}}{2 \cdot N} \cdot 10^{12}Aggregate Tokens/Sec≈2⋅NActive FP16 Tensor TFLOPS×MFU​⋅1012

    On an H100 SXM (989 TFLOPS BF16 dense, assuming 40% MFU on 8B model):

    Aggregate Throughput≈989×1012×0.402×(8×109)≈24,725 tokens/sec across all users\text{Aggregate Throughput} \approx \frac{989 \times 10^{12} \times 0.40}{2 \times (8 \times 10^9)} \approx \mathbf{24,725\text{ tokens/sec across all users}}Aggregate Throughput≈2×(8×109)989×1012×0.40​≈24,725 tokens/sec across all users

    (Each user receives 24,72564≈386 tokens/sec\frac{24,725}{64} \approx 386\text{ tokens/sec}6424,725​≈386 tokens/sec, achieving orders-of-magnitude better compute and hardware cost efficiency).
