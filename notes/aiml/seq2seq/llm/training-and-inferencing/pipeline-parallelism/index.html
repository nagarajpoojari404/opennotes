Pipeline Parallelism Fundamentals

Pipeline Parallelism (PP) partitions a deep neural network sequentially across ppp accelerators (pipeline stages), where stage kkk processes layer chunk kkk and sends boundary activations to stage k+1k+1k+1.

In a standard backward pass of deep learning workloads, computation splits into two distinct operations:

  1. BBB (Activation Gradient / ∇x\nabla_{\mathbf{x}}∇x​): Computes gradients with respect to input activations ∂L∂x\frac{\partial \mathcal{L}}{\partial \mathbf{x}}∂x∂L​ and passes them upstream to stage k−1k-1k−1.
  2. WWW (Weight Gradient / ∇w\nabla_{\mathbf{w}}∇w​): Computes gradients with respect to local parameters ∂L∂w\frac{\partial \mathcal{L}}{\partial \mathbf{w}}∂w∂L​. This computation does not block preceding pipeline stages.

The fundamental trade-off in pipeline parallelism balances three competing factors:

  • Bubble Rate (rbubbler_{bubble}rbubble​): The fraction of GPU time spent idle waiting for upstream activations or downstream gradients.
  • Peak Activation Memory: The maximum number of un-retired micro-batch activation buffers stored concurrently across devices before backward passes consume them.
  • Communication Overhead: The volume of peer-to-peer (P2P) boundary transfers and synchronization barriers across stages.

1. Naive Model Parallelism (Sequential Execution)

The model is partitioned across ppp GPUs, but the entire batch BBB runs sequentially through each GPU without micro-batching.

GPU 0: [ F ]--------------------------------------------[ B ]
GPU 1: ----- [ F ]--------------------------------[ B ]------
GPU 2: ----------- [ F ]--------------------[ B ]------------
GPU 3: ----------------- [ F ]--------[ B ]------------------
Time  ------------------------------------------------------>
  • Execution: GPU 0 computes the forward pass on the entire batch, transmits activations to GPU 1, and idles. The data travels forward to GPU p−1p-1p−1, which computes loss and starts backpropagation back to GPU 0.
  • Bubble Fraction: At any given moment, only 111 of ppp GPUs is active. rbubble=p−1p r_{bubble} = \frac{p - 1}{p} rbubble​=pp−1​ For p=8p=8p=8, 87.5%87.5\%87.5% of all accelerator compute cycles are completely idle.

2. GPipe (Synchronous Micro-Batching)

GPipe splits a mini-batch into mmm independent micro-batches (m≫pm \gg pm≫p). Micro-batches are pushed sequentially through the stages in an accumulated pipeline.

GPU 0: [F1][F2][F3][F4]                        [B4][B3][B2][B1]
GPU 1:     [F1][F2][F3][F4]                [B4][B3][B2][B1]
GPU 2:         [F1][F2][F3][F4]        [B4][B3][B2][B1]
GPU 3:             [F1][F2][F3][F4][B4][B3][B2][B1]
       |<-- Startup Bubble -->|        |<-- Drain Bubble -->|
  • Execution Schedule: All mmm forward micro-batches run first (filling the pipe), followed by an accumulation barrier, and then all mmm backward micro-batches run in reverse order (LIFO or FIFO) before an optimizer step.
  • Bubble Ratio: With forward micro-batch execution time tFt_FtF​ and backward execution time tB≈2tFt_B \approx 2t_FtB​≈2tF​: rbubble=(p−1)(tF+tB)m(tF+tB)=p−1m r_{bubble} = \frac{(p - 1)(t_F + t_B)}{m(t_F + t_B)} = \frac{p - 1}{m} rbubble​=m(tF​+tB​)(p−1)(tF​+tB​)​=mp−1​ To bring bubble overhead under 10%10\%10%, m≥9pm \ge 9pm≥9p is required.
  • Memory Bottleneck: GPU 0 must retain intermediate activations for all mmm micro-batches until micro-batch 1’s backward pass begins: Peak Activation Memory∝O(m) \text{Peak Activation Memory} \propto \mathcal{O}(m) Peak Activation Memory∝O(m) When scaling mmm to reduce bubbles, device memory exhausts rapidly unless activation recomputation (checkpointing) is aggressively applied.

3. 1F1B (One Forward, One Backward)

Introduced in PipeDream and Megatron-LM, 1F1B caps activation memory by scheduling alternating execution: once a stage’s pipeline is warm, it executes exactly one forward pass followed by one backward pass.

Warmup: Stage k executes (p - k) forward passes
Steady State: 1 Forward followed by 1 Backward (1F1B)
Cooldown: Finish remaining in-flight backwards

GPU 0: [F1][F2][F3][F4][B1][F5][B2][F6][B3][F7][B4]...
GPU 1:     [F1][F2][F3][B1][F4][B2][F5][B3][F6][B4]...
GPU 2:         [F1][F2][B1][F3][B2][F4][B3][F5][B4]...
GPU 3:             [F1][B1][F2][B2][F3][B3][F4][B4]...
  • Memory Bound: A stage holds at most ppp active micro-batch activation buffers at any point, completely decoupling memory consumption from the total number of micro-batches mmm: Peak Activation Memory∝O(p) \text{Peak Activation Memory} \propto \mathcal{O}(p) Peak Activation Memory∝O(p)
  • Bubble Ratio: Identical to GPipe: rbubble=p−1m r_{bubble} = \frac{p - 1}{m} rbubble​=mp−1​ 1F1B allows large mmm to lower bubble rates without exhausting VRAM.

4. Interleaved 1F1B

Megatron-LM introduced the Interleaved 1F1B schedule to attack the bubble directly without scaling micro-batches (mmm).

  • Mechanism: Each physical GPU holds vvv non-continuous “virtual stages” (or chunks) instead of 1. For example, with p=4p=4p=4 GPUs and v=2v=2v=2 virtual stages per GPU:
    • GPU 0 hosts Chunk 0 (layers 1–2) and Chunk 4 (layers 9–10).
      • GPU 1 hosts Chunk 1 (layers 3–4) and Chunk 5 (layers 11–12).
      • GPU 2 hosts Chunk 2 (layers 5–6) and Chunk 6 (layers 13–14).
      • GPU 3 hosts Chunk 3 (layers 7–8) and Chunk 7 (layers 15–16).
  • Bubble Reduction: Because each chunk contains 1v\frac{1}{v}v1​ of a stage’s layers, individual compute slots shrink by vvv. The startup and drain bubbles scale down: rbubble=p−1v⋅m r_{bubble} = \frac{p - 1}{v \cdot m} rbubble​=v⋅mp−1​ Setting v=2v=2v=2 halves the bubble overhead for the same mmm.
  • Trade-off: Network communication increases by a factor of vvv because activations and gradients must pass through the physical device ring vvv times per mini-batch.

5. Zero-Bubble Pipeline Parallelism (ZBPP)

Conventional 1F1B treats the backward pass as a single monolithic block (BBB). Zero-Bubble PP exploits the decoupling between activation gradients (BBB) and parameter gradients (WWW):

Sea AI Lab - Sea Limited

  • BBB lies strictly on the critical latency path (upstream stages cannot backpropagate until they receive ∇x\nabla_{\mathbf{x}}∇x​).
  • WWW lies off the critical path (weights are only needed at the end-of-batch optimizer step).
Decomposition:
Standard:  [ F ]  ->  [ Backward (B + W) ]
ZBPP:      [ F ]  ->  [ B (activation grad) ] ... [ W (weight grad) scheduled into idle bubbles ]
  • Scheduling Strategy (ZB1P / ZBV):
    1. Split backward into distinct kernel launches: compute ∇x\nabla_{\mathbf{x}}∇x​ (BBB) first, defer ∇w\nabla_{\mathbf{w}}∇w​ (WWW). 2. Prioritize tasks: B>F>WB > F > WB>F>W. 3. Push WWW tasks into the startup and teardown phases where GPUs normally sit idle waiting for boundary activations.
  • Performance: With tF≈tB≈tWt_F \approx t_B \approx t_WtF​≈tB​≈tW​, the bubble is reduced from p−1m\frac{p-1}{m}mp−1​ down to p−13m\frac{p-1}{3m}3mp−1​ (in ZB1P) or near 0%0\%0% bubble (in ZBV with two virtual stages), without inflating peak activation memory relative to 1F1B.

6. DualPipe (Bidirectional Overlapping Pipeline)

Introduced in the DeepSeek-V3 architecture, DualPipe is designed for Mixture-of-Experts (MoE) architectures running on scale-out clusters where inter-stage communication and cross-node MoE All-to-All communication create severe latency bottlenecks.

Forward Direction 0:   Micro-batches run Stage 0  -> Stage p-1
Reverse Direction 1:   Micro-batches run Stage p-1 -> Stage 0

Physical GPU execution:
Overlaps [Forward / B_grad of Stream 0] with [All-to-All Dispatch / Combine of Stream 1]
  • Bidirectional Workload: The mini-batch is split across two concurrent pipelines flowing in opposite directions:
    • Stream 0 moves forward from GPU 0→p−10 \to p-10→p−1.
      • Stream 1 moves forward from GPU p−1→0p-1 \to 0p−1→0.
  • Fine-Grained Compute-Communication Overlap: DualPipe splits operations into fine-grained units:
    • FFF (Forward compute)
      • BBB (Activation backward compute)
      • WWW (Weight backward compute)
      • CdispC_{disp}Cdisp​ / CcombC_{comb}Ccomb​ (MoE dispatch and combine collective communications)
  • Execution: While a GPU computes FFF or BBB for Stream 0, it overlaps the MoE All-to-All network communication for Stream 1 on independent SM streaming kernels and copy engines.
  • Impact: It eliminates both pipeline bubble latency and network communication waiting time simultaneously, achieving close to 100%100\%100% GPU compute saturation during MoE training.
